## 1. Overview

The **frontend** tier of Polar Forensic Auditor is a high-precision, real-time investigation dashboard built with **Next.js 14 (App Router)**, **React 18**, **TypeScript**, and **Tailwind CSS**. It serves as the primary investigative console for Anti-Money Laundering (AML) compliance officers, forensic auditors, and financial intelligence analysts.
The **Polar Forensic Auditor Frontend** is a high-performance, browser-native forensic investigation console built on **Next.js 14 (App Router)**, **React 18**, **TypeScript**, and **Tailwind CSS**. 

### Current Application Entry Points & Interface Conventions
- **Landing Page (`/`)**: The main landing page introduces the Polar platform, highlighting its hybrid deterministic graph reduction and agentic reasoning capabilities. Action buttons ("Explore the platform", "Explore Polar") navigate directly to `/investigate`.
- **Case File Viewer (`/investigate`)**: The primary workspace, per the [judged case-file contract](../../student-materials/forensic-auditor/case_file_structure.md). Implemented via `app/investigate/page.tsx` and `components/case-file/CaseFileWorkspace.tsx`. Loads a submission JSON (bundled sample, local file, handed off from the Data estate page, or the backend's proposed `/case-file` endpoint), validates it in the browser with the same rules as `validate_format.py`, and renders the full 5-section document — Header, Executive summary, one section per Finding (heading, rule broken, amount & confidence, narrative, money trail diagram, exhibits, reconciliation, adversarial review), Leads investigated and closed, and Method & limits. See [§10](#10-case-file-viewer-and-export-engine).
- **Data Estate (`/investigate/data`)**: Implemented via `app/investigate/data/page.tsx` and `components/estate/DataEstateWorkspace.tsx`. Loads the company's data estate — SQLite `.db`, per-table CSV, CFDI 4.0 XML, or JSON — validates it against `estate_schema.sql` entirely in the browser (via `sql.js` WASM), and lets exhibits in the case file viewer be checked against it. See [§11](#11-data-estate-ingestion).
- **Legacy Simulation (`/investigate/simulation`, deprecated)**: The original frontend-only multi-agent simulation (`components/InvestigationDashboard.tsx`, `hooks/useAgentSimulation.ts`), kept for reference behind a deprecation banner. It predates the judged case-file contract and is not wired to the entry points above. See [§4](#4-legacy-multi-agent-investigation-simulation-engine-deprecated).
It provides compliance officers and competition judges with two interactive investigation workspaces:
1. **Case File Viewer (`/investigate`)**: Institutional forensic document viewer conforming to the HackMTY/Infosys `submission_schema.json` specification, featuring pure deterministic derived state, inline Mermaid money trail rendering, evidentiary exhibit schedules, adversarial review disclosures, and multi-format export (Print/PDF, standalone HTML, Markdown, JSON).
2. **Data Estate Workspace (`/investigate/data`)**: In-browser financial data estate engine using WebAssembly SQLite (`sql.js`), enabling drag-and-drop ingestion of SQLite `.db`, per-table CSVs, CFDI 4.0 XML, and JSON with client-side schema validation against `estate_schema.sql`, cross-examination of case file exhibits, and real-time live audit streaming modal integration (`POST /api/v1/estates/audit/stream`).

- **Interface Language & Theme**: Per platform convention the workspace chrome uses **English** UI labels. The Polar charcoal/ice-blue forensic theme (`#090d16`, `#111827`, `#1f293d`) styles the app shell (header, toolbars, empty states); the case file **document** itself renders on a light "paper" palette (`paper`/`evidence` Tailwind tokens in `tailwind.config.js`) so screen, print, and the HTML export all look like the same institutional document. Narrative text generated by upstream forensic services retains its supplied language.
- **Case File / Data Estate Session**: `app/investigate/layout.tsx` wraps the whole route group in `InvestigateSessionProvider`, so the loaded case file and data estate survive client-side navigation between `/investigate` and `/investigate/data` — but not a page reload, by design (no server-side persistence).
- **Interactive Money Trail Visualization**: The case file's money trail (Task 7) renders via `mermaid` (pinned to `11.17.2`, see §10.2), not `@xyflow/react` — a `flowchart LR` is compiled to inline SVG in the browser, either the run's own `mermaid_source` or one generated from `money_trail` steps. `@xyflow/react` remains the target blueprint for a separate, exploratory graph canvas (documented in [React Flow Architecture Blueprint](./react-flow-blueprint.md)); it is not used by the case file document.

## 4. Legacy Multi-Agent Investigation Simulation Engine (Deprecated)
## 5. Technology Stack & Key Dependencies

> [!WARNING]
> This section documents `components/InvestigationDashboard.tsx` and `hooks/useAgentSimulation.ts`, now served only at `/investigate/simulation` behind a deprecation banner. It predates the judged [case-file contract](../../student-materials/forensic-auditor/case_file_structure.md) and plays no part in `/investigate` or `/investigate/data` — see [§10](#10-case-file-viewer-and-export-engine) and [§11](#11-data-estate-ingestion) for the current workspace. Kept for reference only; do not build on it.
- **Framework**: Next.js 14.2+ (App Router), React 18.3+, React DOM
- **Language**: TypeScript 5.4+ (Strict Mode)
- **Styling**: Tailwind CSS 3.4+, Lucide React (Icons), `clsx`, `tailwind-merge`
- **In-Browser Database**: `sql.js` 1.12.0 (WebAssembly SQLite)
- **Diagrams & Visuals**: `mermaid` 11.17.2 (Client SVG compiler)
- **Data Parsing**: `papaparse` 5.4.1 (CSV streaming/coercion)

To enable offline demonstrations and testing without backend infrastructure, the legacy workspace incorporated a local multi-agent simulation engine via `hooks/useAgentSimulation.ts`:

### 4.1 Ingestion & Parsing
- Ingests 1 to 5 user-supplied CSV files (up to 20 MB total).
- Reads up to 200 rows per file client-side using `FileReader`.
- Performs canonical alias matching for IBM AMLSim column names (`origin`, `destination`, `amount`, `timestamp`).
- Extracts sample account identifiers, transaction amounts, and volume statistics to populate realistic forensic evidence.

### 4.2 Concurrent Specialist Agent Tracks
The simulation executes 5 specialized agent tracks across a synchronized time axis:
1. **Lead Forensic Orchestrator**: Manages investigation lifecycle, delegates sub-tasks, and synthesizes the judicial dictamen.
2. **Ingestion & Data Validation Specialist**: Normalizes transaction ledgers, filters zero-balance noise, and validates schema integrity.
3. **Circular Flow Specialist**: Extracts directed cycles and uncovers circular layering (*smurfing*) rings.
4. **Pass-Through Velocity Analyst**: Analyzes high-velocity transit accounts with flow retention ratios $\ge 90\%$ within $\le 48\text{h}$.
5. **Risk & Legal Compliance Auditor**: Cross-references findings against Mexican tax/AML statutes (CFF Art. 69-B, NIF A-2, UIF ROI guidelines).

### 4.3 Simulation Integrity & Transparency
- Persistent disclaimers clarify that the simulation is illustrative and does not connect to external AI models or financial institutions.
- Resetting the investigation cancels all pending execution timers and cleanly resets local component state.

## 8. Edge Cases, Performance & Gotchas

### 8.1 Missing Utility Module (`@/lib/utils.ts`)
- **Issue**: Standard `.gitignore` rules with `lib/` can inadvertently ignore `frontend/lib/utils.ts`.
- **Resolution**: Ensure `.gitignore` anchors rules to root (`/lib/`) so `frontend/lib/utils.ts` (`cn`, `formatCurrencyMXN`) remains tracked in source control.

### 8.2 Browser `EventSource` Protocol Constraints
- Standard browser `EventSource` only supports HTTP `GET` requests and cannot supply custom headers (such as `Authorization: Bearer <token>`).
- If token authorization is required in production, pass an ephemeral query token or utilize `@microsoft/fetch-event-source`.

### 8.3 Object URL Garbage Collection
- `useAudioStream` converts audio responses into in-memory `Blob` objects and creates temporary URLs via `URL.createObjectURL(blob)`.
- Always track active URLs in a `useRef` and explicitly call `URL.revokeObjectURL(url)` during teardown or before generating a new audio clip to prevent browser memory leaks.

### 8.4 Client-Side Directive (`"use client"`)
- Every component consuming browser APIs (`EventSource`, `HTMLAudioElement`, `FileReader`, DOM scrolling) must declare `"use client"` at the top of the file to prevent SSR hydration errors in Next.js.

### 8.5 Separation of Simulation and Live Analysis
- When enhancing the UI, maintain strict architectural separation between local simulation (`useAgentSimulation`) and live backend analysis (`useInvestigationStream`). Never fabricate backend requests in simulation mode.

### 8.6 A Bare `data` Pattern in `.gitignore` Swallowed `frontend/app/investigate/data/`
- **Issue**: the root `.gitignore` ignored the AMLSim `data/` folder with a bare `data` pattern, which (like the historical bare `lib/` pattern in 8.1) matches a directory named `data` at *any* depth — including the case file's `app/investigate/data/` route.
- **Resolution**: anchored to `/data` so only the repo-root folder is ignored. If a future `.gitignore` edit reintroduces a bare pattern that collides with a frontend path, anchor it the same way rather than renaming the frontend path.

### 8.7 `mermaid` and `sql.js` Version Pins
- `mermaid` is pinned to `11.17.2` (exact, not `^`). `mermaid@12` requires Node ≥ 22.12; this repo targets Node 20 (`node:20-alpine` in the Dockerfile, and locally). Do not bump the major version without also bumping the Node target everywhere.
- `sql.js` (`1.14.2`) and `papaparse` (`5.7.0`) are pinned exact for the same reason: deliberate, reviewed upgrades only. sql.js's WASM binary is fetched from `/sql-wasm.wasm` (see the build-nuances note above), never from a CDN, so the Data estate page keeps working with the network disabled.

## 10. Case File Viewer and Export Engine

### 10.1 Data Contract: Superset of `submission_schema.json`

`types/caseFile.ts` mirrors [`student-materials/forensic-auditor/submission_schema.json`](../../student-materials/forensic-auditor/submission_schema.json) exactly for every field and enum the judges' `validate_format.py` checks (`scheme_type`'s 5 values, `source_table`'s 8 tables, `confidence`, `closed_by`, entity id prefixes, exhibit/reconciliation shapes). Fields the official schema does not define — `header`, `executive_summary`, `rule_detail`, `reconciliation.matched_table`/`per_table_breakdown`, `adversarial_review`, `mermaid_source`, `closure_category`, `method_and_limits` — are optional extensions the renderer reads when present and derives sensible defaults for when absent. A submission missing every extension still renders correctly; `validate_format.py` never sees or requires them.

| Extension field | Where it renders | Falls back to |
| :--- | :--- | :--- |
| `header.{company,company_rfc,audit_period}` | Task 1 header | "not reported" |
| `executive_summary.plain_narrative` | Task 2 | a generated summary from the findings |
| `findings[].rule_detail.{code,authority,article,legal_text_citation}` | Task 4 | `rule_broken` text only, optionally matched against `lib/caseFile/constants.ts::RULE_CATALOG` by code |
| `findings[].mermaid_source` | Task 7 diagram | generated from `money_trail` via `lib/caseFile/mermaid.ts::buildMermaidFromTrail` |
| `findings[].reconciliation.{matched_table,per_table_breakdown}` | Task 9 | derived in the browser from `exhibits[].amount` (or from the loaded data estate — see §11) |
| `findings[].adversarial_review` | Task 10 | "No adversarial review was recorded for this finding." |
| `leads_not_pursued[].closure_category` | Task 11 tag | "Unclassified" |
| `method_and_limits.*` | Task 12 | "Not provided by this run." per subsection |
| `run_metadata.cost_by_role` | Task 1 cost line | omitted |

### 10.2 Pipeline: Source → Normalize → Validate → Derive → Render

1. **Source** (`hooks/useCaseFileSource.ts`): a bundled fixture (`fixtures/*.json`, dev-only picker), a local `.json` file (drag-drop or browse, max 5 MB), a raw object handed off from the Data estate page (`loadRaw`), or the backend endpoint behind `NEXT_PUBLIC_CASE_FILE_API=enabled`.
2. **Normalize** (`lib/caseFile/normalize.ts`): converts the raw parsed JSON into a lenient `CaseFileDocument` that always renders — missing/malformed fields become `null`/`""`/`[]`, never a crash.
3. **Validate** (`lib/caseFile/validate.ts`): `validateStructure()` is a line-for-line TypeScript port of `validate_format.py::validate_structure`, operating on the **raw** JSON (not the lenient document) so its messages, error codes, and ordering match the Python validator exactly — this is what `ValidationPanel` and the format-check chip in `ExportToolbar` show. `collectWarnings()` adds renderer-side quality warnings beyond the Python script's scope (missing optional sections, a `rule_broken` that reads as a statistical description, a disconnected money trail, a generic-sounding declined-lead reason).
4. **Derive** (`lib/caseFile/derive.ts::buildCaseFileView`): builds the presentation view model — entity display names, per-finding money-trail step linking, and reconciliation arithmetic (mirrors `validate_format.py::validate_against_estate`'s per-table, best-matching-table logic). Pure and deterministic: the same document always produces the same view, and warnings/derived values never depend on `Date.now()`, `Math.random()`, or `new Date(...)` parsing (dates are always shown as the run's own ISO strings).
5. **Render** (`components/case-file/*`): `CaseFileDocument.tsx` assembles the five sections in the required order; each Finding is a `Collapsible` card (`CaseFileUiContext` tracks open/closed state and, per finding, whether its Mermaid diagram has settled).

### 10.3 Money Trail Diagrams (`lib/caseFile/mermaid.ts`)

- `mermaid` is loaded via a single dynamic `import("mermaid")`, initialized once (`securityLevel: "strict"`, `deterministicIds: true` so the same source always produces the same SVG ids), and every render is serialized through one queue — mermaid is not safe to call concurrently, and React 18 Strict Mode double-invokes effects.
- `MermaidDiagram.tsx` tries the run's own `mermaid_source` first; if it fails to parse/render, it falls back to `buildMermaidFromTrail()`'s generated `flowchart LR` and reports which source actually rendered to `CaseFileUiContext` (`diagrams[anchorId].renderedSource`/`usedFallback`) — that reported source, not a static guess, is what the figure caption, the Markdown export, and `diagramsSettled` (which gates every export button) all read.

### 10.4 Format Checking Without a Network Call

`fixtures/case-file.sample.json`, `case-file.no-findings.json`, and `case-file.edge-cases.json` are checked into the repo and exercised against the *actual* `validate_format.py` as part of verifying this feature (not just the TS port): the first two must `PASS`, and the third must fail with exactly 10 named errors (see `doc/frontend/case-file-plan.md` Appendix B for the literal fixture contents and expected error list). Re-run those checks after touching `lib/caseFile/validate.ts` or the fixtures:

```bash
python -X utf8 student-materials/forensic-auditor/validate_format.py --submission frontend/fixtures/case-file.sample.json
python -X utf8 student-materials/forensic-auditor/validate_format.py --submission frontend/fixtures/case-file.no-findings.json
python -X utf8 student-materials/forensic-auditor/validate_format.py --submission frontend/fixtures/case-file.edge-cases.json
```

### 10.5 Export Engine (Task 13)

`components/case-file/ExportToolbar.tsx` offers four outputs, all built from the already-rendered DOM/view — no server round-trip:

| Format | How | Notes |
| :--- | :--- | :--- |
| Print / PDF | `window.print()` | `app/globals.css`'s `@media print` block hides interactive chrome (`[data-print="hide"]`), forces every collapsed section and filtered table row back open (`[data-collapsible-body][hidden]`, `tr[data-filterable-row][hidden]`), and paginates one Finding per page. |
| HTML | `lib/caseFile/toHtml.ts::buildStandaloneHtml` | Clones `#case-file-document`, strips `[data-export="exclude"]`/`[data-print="hide"]` nodes, force-opens the same collapsed/filtered elements as print, inlines every stylesheet, and embeds the original submission JSON in a `<script type="application/json" id="case-file-data">` tag. Self-contained: no external `<script src>`, no CDN references. |
| Markdown | `lib/caseFile/toMarkdown.ts::buildCaseFileMarkdown` | Deterministic string builder (not a DOM clone); embeds each finding's actual rendered Mermoid source in a ` ```mermaid ` fence. |
| JSON | — | The original loaded `raw` object, pretty-printed — a no-op round trip so a judge always has the exact machine-checked file alongside the human-readable ones. |

All four buttons are `disabled` until `CaseFileUiContext.diagramsSettled` is true, so an export never fires while a Mermaid diagram is still attempting to render. In development, `window.__caseFileDebug` (`{ buildMarkdown, buildHtml, issues }`) is set on every render so these exporters can be exercised from the browser console without clicking through the UI. The export actions live in `hooks/useCaseFileExports.ts`, shared by the toolbar and the tour's closing screen.

Print and HTML are built from `CaseFileDocument`, which `CaseFileWorkspace` keeps mounted but hidden on screen (`hidden print:block`) — the screen shows the guided tour (§10.6) instead. Its diagrams are the ones that report to `diagramsSettled`.

### 10.6 Guided Tour (`components/case-file/tour/*`)

On screen the case file is a chapter-by-chapter tour: Case opening → Executive summary → one chapter per finding → Leads investigated and closed → Method and limits → Review route. The reader advances only with the **Continue** button (nothing auto-advances); the sticky progress rail jumps to any chapter; Review route lets the reader reopen any part or **Conclude report**, which shows a closing screen with the four exports.

- **Chapters** — `lib/caseFile/tour.ts::buildTourChapters(view, layout)`. `layout` is `"single"` (default: a finding is one screen with a scrollspy block index and blocks revealed on scroll) or `"steps"` (each finding splits into accusation / what happened / evidence / adversarial review). The choice is a toggle in the rail, persisted in `localStorage` (`polar.caseTour.findingLayout`); chapters share a layout-independent `baseKey` so switching keeps the position.
- **Navigation** — `hooks/useTourNavigation.ts` tracks the active chapter by identity, keeps the outgoing chapter mounted for its 220 ms exit animation, and records visited parts. After each change `CaseFileTour` scrolls the stage into view, focuses the chapter heading, and announces the position through an `aria-live` region.
- **Theming** — `paper.*`/`evidence.*` Tailwind colors resolve through `--case-*` CSS variables (`app/globals.css`): `.case-paper` (the printable document) uses a neutral light palette, `.case-tour` maps the same tokens to the portal's dark palette, so the document's section components are reused inside the tour unchanged. Use `bg-paper-sheet` / `text-evidence-on` instead of `bg-white` / `text-white` in those components.
- **Diagrams** — `MermaidDiagram variant="tour"` renders a dark-themed SVG (`renderMermaidSvg(id, themeDiagramSource(source, "dark"), "dark")`, cached per theme/source; the flagged `classDef` is re-themed for run-supplied sources too) and does not report to `CaseFileUiContext`. Every render — tour or document — goes through the off-screen `.mermaid-sandbox` in `lib/caseFile/mermaid.ts`, because the global reduced-motion `* { transition-duration }` override otherwise makes Mermaid measure SVG geometry mid-transition and emit a huge, off-center viewBox.
- **Money trail player** — in the tour, `MoneyTrail` delegates to `tour/MoneyTrailPlayer.tsx`. `lib/caseFile/trailScene.ts::buildTrailScene(svg, trail)` indexes the mounted SVG (nodes by `{svgId}-flowchart-{id}-{n}`, edges by `data-id="L_{from}_{to}_{n}"`, steps by a `Step N` label or 1:1 definition order; `synced` is false when neither maps cleanly). `hooks/useTrailPlayback.ts` renders every visual as a function of (stop, elapsed ms) from one `requestAnimationFrame` loop — edge draw, a money packet along `getPointAtLength`, a label fade, an arrival ring on the receiving node — so pause, jump and replay always settle to a correct state; states are `data-trail-state="pending|active|dim"` styled in `globals.css`. Controls: play/pause, previous/next, replay, step pills, Fit/100% (100% pins the viewBox width), keyboard (`←/→`, `Space`, `Home/End`, `Esc`) on the canvas, hover an entity to trace its flows, and a `MoneyTrailTimeline` whose rows follow and drive the diagram when `synced`.
- **Motion** — CSS keyframes (`tour-*` in `globals.css`), animating `transform`/`opacity`; counters use `hooks/useCountUp.ts`. `prefers-reduced-motion` removes delays and loops and shows final values immediately. The money trail player is JS-driven and follows `hooks/useTrailMotionPreference.ts`: OS preference by default (no autoplay, instant highlights, stepping still works) with an **Animate** toggle, shown only when the OS reduces motion, that forces motion for the session (`sessionStorage` `polar.trailMotion`). Otherwise it autoplays once when the diagram scrolls into view and pauses when it leaves the viewport or the tab is hidden.
- **Exhibit chips** in a money-trail timeline are intercepted inside the tour: in step-by-step mode they open the finding's Evidence chapter, then scroll to and highlight the row.

## 11. Data Estate Ingestion

### 11.1 Why It Exists

The judged pipeline ingests an `estate_schema.sql`-shaped SQLite database, not the AMLSim CSVs `backend/services/ingestion.py` currently reads (see [`doc/data-and-compliance/README.md`](../data-and-compliance/README.md)). Until the backend seeder/ingestion catches up to that contract, `/investigate/data` lets a judge (or a developer) assemble and inspect that data estate **entirely in the browser** — no backend, no network call — and hands the case file viewer a way to check every exhibit's `record_id` against it, mirroring `validate_format.py --estate`.

### 11.2 Supported Formats (`lib/estate/*`)

| Format | Parser | Table detection |
| :--- | :--- | :--- |
| SQLite `.db`/`.sqlite`/`.sqlite3` | `sqlite.ts::parseSqliteFile` (via `sql.js` WASM) | Reads `sqlite_master`; imports the 8 known tables by name, warns on unknown ones. |
| CSV | `parseCsv.ts::parseCsvFile` (via `papaparse`) | By filename suffix first (`vendors.csv`, `export_invoices.csv`), then by header-column match ratio (≥ 60%, primary key required). Undetected → held as `pendingCsv` until the user picks a table in `EstateFileList`. |
| JSON | `parseJson.ts::parseJsonFile` | An object keyed by table name, a bare array named after its table (filename-detected), *or* a case-file submission — the last of those is hand-off to the case file viewer, not the estate (see 11.3). |
| XML | `parseXml.ts::parseXmlFile` | A CFDI 4.0 `<Comprobante>` (one `invoices` row; namespace-agnostic element lookup since PAC namespaces vary) or an `<estate>`/single-table document with `<row>` children. |

Every parser routes rows through `coerce.ts::coerceRow`, which matches columns case-insensitively against `ESTATE_SCHEMA` (`schema.ts`, a literal mirror of `estate_schema.sql`), coerces `TEXT`/`REAL`/`INTEGER` per column, and reports unknown/missing columns once per file (not once per row).

### 11.3 CFDI 4.0 Field Mapping

CFDI XML never carries SAT cancellation status, so `invoices.status` is always `null` with a `W_CFDI_STATUS_UNKNOWN` warning — provide it via CSV/JSON if known. The Comprobante-level `<Impuestos TotalImpuestosTrasladados="...">` (a **direct child** of `Comprobante`, never the one nested inside a `<Concepto>`, which covers only that line item) is what backs `invoices.iva`; if absent, it's summed from that node's own `<Traslado Impuesto="002">` entries.

### 11.4 Estate-Wide Validation (`validateEstate.ts`)

After folding every imported file's contributions (first occurrence of a primary key wins; a later duplicate is reported and dropped), `buildEstate()` runs RFC/CLABE/ISO-date format checks, CFDI enum checks (`metodo_pago`, `invoices.status`, `channel`, `efos_list.status`), invoice arithmetic (`iva ≈ 16% × subtotal`, `total ≈ subtotal + iva`), and referential integrity (`purchase_orders`/`contracts.vendor_rfc` against `vendors`, `ledger.invoice_uuid` against `invoices`). `hooks/useEstate.ts` exposes `issues` as every file's own `fileIssues` **plus** `buildEstate()`'s estate-wide issues — read from there, not from `buildEstate()` alone, to see the full picture.

### 11.5 Checking Exhibits Against the Estate (`estateCheck.ts`)

`validateAgainstEstate()` is a browser-side, line-for-line port of `validate_format.py::validate_against_estate`: every exhibit's `record_id` must resolve in the loaded estate table, and `peso_amount` must reconcile (≤ 2%) to the best-matching amount-bearing table's sum, computed **per table** the same way the Python script does. `lib/caseFile/derive.ts::buildCaseFileView(document, estate)` uses this to give each exhibit an `estateStatus` (`"found" | "missing" | "not_checked"`) and prioritizes an estate-backed reconciliation over the run's own `reconciliation` object or a derived one — reflected in `ExhibitsTable`'s "in estate"/"not in estate" badges and the "Estate check" chip in `ExportToolbar`.

### 11.6 Export (`sqlite.ts::exportEstateSqlite`)

"Download estate.db" runs the literal `ESTATE_DDL` (copied from `estate_schema.sql`) against a fresh in-memory `sql.js` database and inserts every folded row, producing a real SQLite file a judge can hand straight to `validate_format.py --estate estate.db` offline. Round-tripped and cross-checked while building this feature: `frontend/public/samples/estate/*` exports to a `.db` that, together with `frontend/fixtures/case-file.sample.json`, passes `validate_format.py --estate`, and together with `case-file.edge-cases.json` produces exactly its 10 structural errors plus 3 estate-reconciliation errors.
